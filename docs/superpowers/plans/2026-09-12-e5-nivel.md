# E5 — avaliação de nível 1

Fecha a trilha E5. Spec: `docs/planejamento/02-trilha.md` (saída do Nível 1) —
**30 itens mistos (todas as tags do nível) + escrita (ticket completo) +
simulação (standup + pedir ajuda). Aprovação: ≥ 75 % e simulação ≥ 3/5.
Compara radar com o teste inicial.**

O engine já suporta `kind: "level"` (`server/assessment.ts`, `db.ts`), mas não
há schema de conteúdo, carregamento, elegibilidade, rotas nem página.

## Escopo

Infra mínima + conteúdo + testes. Sem dependências novas.

- **T1 — schema e loader**: `LevelAssessmentSchema` em `shared/schema.ts`
  (`id: "L1"`, `title`, `intro`, `items` (30), `writing`, `speaking`,
  `pass` fixo `itemsMin 0.75, writingMin 3.5, speakingMin 3` — writingMin 3,5
  honra o ticket completo e mantém o padrão do nível; a "simulação ≥ 3/5" é a
  fala). Bundle ganha `levelAssessments: Record<string, LevelAssessment>`;
  loader lê `content/levels/level-N.yaml`.
- **T2 — elegibilidade e rotas**: `levelEligibility` em
  `server/assessment.ts` — módulos do nível todos aprovados (`passed: true`
  em `assessments`), lista os que faltam. Rotas `/api/levels/:n/assessment/`
  `state | writing | speaking | finish`, espelhando as de módulo
  (`kind: "level"`, `ref: "L1"`).
- **T3 — conteúdo**: `content/levels/level-1.yaml` — 30 itens cobrindo as
  tags `gram.*/br.*/vocab.*` reais das 30 aulas (levantamento programático),
  ≥ 4 tipos de exercício, gabarito balanceado, stems novos; escrita = ticket
  completo (80–120 palavras, `writingMin` implícito 3,5); fala = simulação
  standup + pedir ajuda em um take de 90 s (`maxSeconds: 90`, expressões-alvo
  dos seis módulos).
- **T4 — guarda**: estender `checkAssessment` para avaliações de nível
  (30 itens, cobertura de tags do nível, ≥ 4 tipos, balanceamento, stems
  novos) + testes de variante para itens com duas correções.
- **T5 — página no cliente**: reutilizar o fluxo de `ModuleAssessment.tsx`
  (itens → escrita → fala → resultado). Opção mínima: página
  `LevelAssessment.tsx` + card de desbloqueio em `Levels.tsx`/`Module.tsx`
  quando os 6 módulos estiverem aprovados. UI sem teste automatizado —
  verificação no navegador.
- **T6 — validação e fechamento**: API na cópia do banco (elegível só com os
  6 módulos aprovados, fluxo completo, 409 idempotente), `AGENTS.md`,
  desvios, ledger, build.

## Riscos

- **Elegibilidade por módulo aprovado** (não só aulas concluídas): precisa
  consultar `assessments` com `passed` — função nova, teste com banco
  `:memory:`.
- **30 itens × ~30 tags do nível**: itens com duas correções cobrem duas tags
  cada; a guarda exige cobertura total — levantamento programático das tags
  reais antes de escrever.
- **"Simulação ≥ 3/5"**: o motor de fala é o modo A (transcript + duração).
  A "simulação" vira a gravação de 90 s com expressões-alvo dos dois cenários;
  desvio registrado.
- **`checkExercise` em `error_correction` com duas correções**: cada variante
  aceita precisa das duas; testes de variante garantem.
- **UI**: rota nova `/levels/1/assessment`; manter o mesmo padrão visual do
  módulo. Sem testes de UI — validação manual no Chrome.

## Fora de escopo

- Radar "compara com o teste inicial" — já existe no painel; não é requisito
  desta entrega.
- Níveis 2–5 — o schema é genérico, mas só `level-1.yaml` entra.

## Resultado (2026-09-12)

Implementado na `feat/e5-nivel`:

- `LevelAssessmentSchema` (id `L\d`, ≥ 30 itens, `pass` com default 0.75/3.5/3) + loader de `content/levels/level-*.yaml` com cross-validation (nível existe na trilha, ids `L<n>-A*`, tags e shape válidos).
- `levelEligibility` em `server/assessment.ts`: conta só o **último** registro por módulo com `passed === true` (não basta aula concluída).
- Rotas `/api/levels/:n/assessment/{state,writing,speaking,finish}` espelhando as de módulo; `assessmentIds` aceita refs `L<n>` em `/api/attempts`.
- `content/levels/level-1.yaml`: 30 itens cobrindo as **59 tags** `gram/br/vocab` reais das 30 aulas (guarda `checkLevelAssessment` valida cobertura, stems novos inclusive contra as avaliações de módulo, gabarito MC balanceado e modelos limpos no detector BR).
- `src/pages/LevelAssessment.tsx` + rota `/levels/:n/assessment` + card na trilha (`Levels.tsx`) travado até os 6 módulos passarem.
- Escrita = ticket completo (80–120 palavras, `writingMin: 3.5`); fala = 90 s juntando standup + pedir ajuda (`speakingMin: 3`).

### Desvios

- "Simulação ≥ 3/5" virou a gravação modo A de 90 s com expressões-alvo dos dois cenários (standup + pedir ajuda) — o motor de fala só tem modo A.
- `br.until-late` coberto só no sentido de reformulação/concisão (o projeto não o trata como erro universal).
- Elegibilidade no cliente deriva de `overview.modules[].passed`; o cadeado real é o servidor (`levelEligibility`).

### Validação

- `content:validate` ok · **492/492 testes** (33 arquivos) · typecheck e build limpos.
- API na cópia do banco (`/tmp/maga-e5-validation`): state elegível 6/6 → `finish` prematuro 409 → 30 itens aceitos → item com ref errado 400 → escrita nota 4 (0 findings BR) → fala 4,5 (90 s) → `finish` **passed** → segundo `finish` 409 → registro `level|L1` no banco.
- UI sem teste automatizado — verificar visualmente `/trilha` (card travado/destravado) e `/levels/1/assessment`.
